# カスタムシステムプロンプト（性格・口調・ルール事前設定）機能 追加仕様案

Sep 28, 2026 · @Masataka Koguchi

**位置づけ**: 本書はこの機能の検討過程を記録した提案ドキュメントであり、7 章のフェーズ A・B は実装済みで本編仕様書（`docs/Hitorigoto 仕様書.md` §7.2、§8）に統合済み。本書は今後の参照用に残す。5 章の実機検証（フェーズ C）は予備的な確認のみ済んでおり、本格的な評価は未実施のまま残課題（8 章）としている。

**実装済みの範囲（本書の提案からの変更点）**

- フェーズ A・B（4 章の機能要件）は実装済み。データモデル・UI・合成順は 4 章の設計どおり。
- 当初の提案になかった追加として、プリセットとは別に「常時適用する指示」（1 つだけ設定でき、プリセットの選択に関わらず全会話へ適用。オン/オフの切り替えなし）を実装した。ユーザーからの追加要望を受けたもので、8 章の「プリセットをアプリ全体の既定値にするか」という論点への回答にもなっている（プリセットは会話ごとの選択、常時適用する指示は別枠のアプリ全体設定、という二本立てで決着）。
- 「全履歴を削除」でプリセット・常時適用する指示をどう扱うかも、実装時にユーザーと合意して確定した（6 章末尾・8 章を参照）。

## 1. 目的

チャット開始前にモデルへ渡す基本指示（性格・口調・禁止事項などのシステムプロンプト）を、ユーザーが画面から設定できるようにする。複数のプリセットを保存でき、トップページ（チャット画面）のプルダウンなどから選んで使い分けられることが望ましい。

Gemini Nano はクラウド LLM と違ってリソースが小さいオンデバイスモデルであるため、単純に「システムプロンプト入力欄を足す」だけでは済まない。以下 2 点が事前に不明であり、検証が要る。

1. システムプロンプトにどの程度のトークン量までなら実用上許容できるか（会話本体を圧迫しない量）。
2. 与えた指示（性格・口調・ルール）が、どの程度忠実に応答へ反映されるか。

本書は、この 2 点についてネット上の公開資料を調査した結果と、その結果を踏まえた機能仕様案・検証計画をまとめる。

## 2. 事前調査のまとめ（Web 資料の有無と内容）

公式ドキュメント（Chrome for Developers）と、Chromium の開発者向けディスカッション、技術ブログを調査した。**Gemini Nano のシステムプロンプトに特化した定量的な資料（「◯文字までなら指示追従率◯%」のような数値データ）は見つからなかった。** 得られたのは以下の定性的な情報にとどまる。

| 項目 | 資料からわかったこと | 出典 |
| --- | --- | --- |
| システムプロンプトの与え方 | `LanguageModel.create()` の `initialPrompts` に `{ role: 'system', content: ... }` を渡す。セッション作成時に渡す方が、初回 `prompt()` に埋め込むより初回応答が速い | [Prompt API](https://developer.chrome.com/docs/ai/prompt-api), [Built-in AI APIs: Do and don't](https://developer.chrome.com/docs/ai/built-in-ai-dos-donts) |
| コンテキストオーバーフロー時の扱い | コンテキストウィンドウが埋まって古い会話が破棄されても、**システムプロンプトは破棄されない**（優先的に保持される） | [Prompt API](https://developer.chrome.com/docs/ai/prompt-api) |
| コンテキストウィンドウの大きさ | 資料により数値がばらつく（4096 トークン、6144 トークン、「1 プロンプトあたり 1024 トークン・セッション全体で直近 4096 トークン保持」など、いずれも古いプレビュー版 API 時点の情報）。本アプリが実機（Chrome 154 相当）で確認した値は `contextWindow` = **9216 トークン**（`src/lib/nano.ts` の `FALLBACK_WINDOW` に既出）で、これが現時点で最も新しく信頼できる数値 | [Maximum Token Limits for Gemini Nano APIs（Google Groups, 2024年時点の情報）](https://groups.google.com/a/chromium.org/g/chrome-ai-dev-preview-discuss/c/WO2NIK_9Ue4), 本リポジトリの実測（`CLAUDE.md` / `nano.ts`） |
| 指示追従性（instruction following） | 「オンデバイスモデルはクラウド版よりシステムプロンプトへの追従が緩い」「フォーマットを守らせたいときはシステムプロンプト内に one-shot の例を入れて固定するとよい」という定性的な助言はあるが、指示の長さと追従率の関係を示す実験データは見当たらなかった | 各種技術ブログ（Thinktecture 社ブログ等）、Chrome 公式 [Built-in AI APIs: Do and don't](https://developer.chrome.com/docs/ai/built-in-ai-dos-donts) |
| 入力最適化の一般論 | 「不要なメタデータ・HTML タグ・フィルタ前の大量リストを送らない」「入力が大きいほど遅延が増える」という一般的な助言はあるが、これはシステムプロンプト固有の話ではない | [Built-in AI APIs: Do and don't](https://developer.chrome.com/docs/ai/built-in-ai-dos-donts) |

**結論**: 「システムプロンプトの適正な長さ」「指示がどの程度反映されるか」を裏付ける公開の定量データは存在しない。したがって、ユーザーが当初懸念していたとおり、**本アプリ自身で実機（実際に Nano をダウンロードした Chrome）を使った検証が必須**であり、検証なしに具体的な上限値やコピー文言を確定できない。5 章に検証計画を示す。

## 3. 現状の実装整理（この機能が触る場所）

- `src/lib/nano.ts` の `SYSTEM_PROMPT`（ja/en 固定文言、`build()` 内で `initialPrompts` の先頭 `system` ロールとして渡される）が現在の唯一のシステムプロンプトである。要約時は `SYSTEM_PROMPT + 要約導入文 + 要約本文` を連結して 1 つの `system` メッセージにしている（`nano.ts:145`）。**Prompt API の `initialPrompts` は `system` ロールを 1 つしか受け付けない前提の実装になっている**ため、カスタム指示も「複数のシステムメッセージ」ではなく、この連結の一部として合成する必要がある。
- コンテキストウィンドウは実測 9216 トークン（`FALLBACK_WINDOW`）で、`COMPRESS_THRESHOLD`（0.8）を超えると要約が走る。システムプロンプトは 2 章のとおり要約されても消えない＝**常に毎ターンの予算を恒久的に消費する**。カスタム指示を足す分だけ、要約が発生するまでの余裕（実質の会話ターン数）が減る。
- 言語切り替え時は `NanoSessions.setLang()` がセッションを破棄して作り直す（`nano.ts:121`）。カスタム指示の切り替えも同様に、既存セッションを破棄して次回ターンで再構築する形が自然に合う。
- ペルソナ的な設定は現状ゼロで、`Thread` 型（`src/lib/history.ts`）にも該当フィールドはない。

## 4. 機能要件（案）

### 4.1 データモデル

新しい概念「プロンプトプリセット」を導入する。

```ts
type PromptPreset = {
  id: string
  name: string          // 一覧・プルダウンでの表示名
  content: string        // システムプロンプト本文（ユーザー自由入力）
  createdAt: number
  updatedAt: number
}
```

- 保存先は履歴と同じ `HistoryRepository` 系（`history.ts` / `history-idb.ts`）にコレクションを追加する形にする。理由: すでに `HistoryQuotaError` によるエラー通知、`BroadcastChannel` によるタブ間同期、`usage()` によるストレージ使用量表示の仕組みがあり、それを再利用できるため。ローカルストレージ版では `presets` キーに配列で保持し、IndexedDB 版では新しい object store `presets` を追加する（スキーマバージョンを上げる）。
- `exchange.ts` のエクスポート/インポート形式（`hitorigoto-export`）にプリセットを含める。現行は v2（drafts・画像対応）なので **v3** に上げ、v1/v2 ファイルの読み込みは従来どおり許容する。

### 4.2 スレッドとの関連付け

- `Thread` 型（`history.ts`）に `presetId?: string` を追加する。スレッドごとに使用中のプリセットを記憶し、後から見返したときにどの指示で会話したかが分かるようにする。
- 一時チャット（保存しないモード）でも選択自体は可能だが、当然ながら `presetId` は保存されない。

### 4.3 UI

- **管理 UI**: `MetricsDialog.tsx` / `GuideDialog.tsx` と同じ `Dialog.tsx` ベースのモーダルで新規作成。プリセットの一覧・追加・編集・削除・複製ができる、簡単な CRUD 画面（`PresetsDialog.tsx` を想定）。文字数カウンターと、後述するトークン概算・注意書きをその場に表示する。
- **選択 UI（トップページ）**: `Header.tsx` の言語セレクトと同じ見た目のプルダウンを追加する（「指示なし（デフォルト）」＋登録済みプリセット一覧＋「プリセットを管理…」）。選択はスレッド単位の状態として `Chat.tsx` 側で保持し、`NanoSessions` に渡す。
- プルダウンでの切り替えは、`setLang` と同様に現在のセッションを破棄し、次回の発話でシステムプロンプトを含めて再構築する。会話の途中で切り替えても過去の応答は変わらない（既存の言語切り替えと同じ挙動に揃える）。

### 4.4 `nano.ts` 側の合成方法

`SYSTEM_PROMPT[lang]` は「日本語/英語で答える」という、アプリの UI 言語保証に関わる非交渉の指示なので、カスタムプリセットで**上書きはせず追記**する。要約との合成順は以下のようにし、優先順位が高いものを先頭に置く。

```
SYSTEM_PROMPT[lang]
（改行）
プリセット本文（設定されていれば）
（改行、要約がある場合のみ）
SUMMARY_INTRO[lang] + 要約本文
```

`NanoSessions` に `setPreset(preset: PromptPreset | null)` を追加し、`setLang` と同じパターン（変更がなければ何もしない、変更があればサマリーを保持したままセッションのみ破棄）で実装する。

## 5. トークン予算・指示追従性の検証計画

2 章の調査結果のとおり、外部資料だけでは「何文字までなら安全か」「指示がどの程度効くか」を決められない。以下の手順で、実機（Nano をダウンロード済みの実 Chrome）を使って自前で検証し、その結果をもってデフォルトの上限値・警告文言・UI コピーを確定する。

**予備確認（2026-09-28、実装直後の簡易確認）**: 日本語で 250 文字前後の常時適用する指示・プリセットは問題なく動作し、プルダウンでのプリセット切り替えによる応答の変化もおおむね想定どおりだった。ただし 5.1・5.2 で定義した手順（長さを段階的に振った比較、固定の質問セットでの人手評価）を踏んだ検証ではなく、あくまで動作確認レベルの結果である。デフォルトの推奨上限文字数・警告文言は、この予備確認の結果だけでは確定させず、5.1・5.2 を実施してから見直す。

### 5.1 トークン予算側の検証（機械的に測れる部分）

1. `session.contextWindow`（実測 9216）を基準に、プリセット本文の推奨上限を **コンテキストウィンドウの 1 割前後（目安 800〜900 トークン、日本語換算で概ね 500〜600 文字、`nano.ts` の実測値 "日本語は概ね 0.65 トークン/文字" を根拠にする）** を初期の目安として設定し、実機で以下を確認する。
   - この量のプリセットを設定した状態で、通常の会話が何ターンほど要約なしで続けられるか（`MetricsDialog` の実行ログで確認できる）。
   - プリセット自体が原因で `QuotaExceededError` になる長さ（上限）はどこか。
2. 管理 UI に文字数カウンターと概算トークン数（`chars * 0.75` の既存の見積もり関数を流用）を表示し、目安を超えたら警告色にする。ハードリミットは設けず、実機検証で決めた値を「推奨」として示すにとどめる（Nano のバージョン差でウィンドウサイズが変わりうるため、`contextWindow` の実測値に対する相対値で警告を出す設計にする）。
3. これは `npm test`（モック `LanguageModel`）でも自動化できる範囲: 「プリセットが `initialPrompts` の `system` に正しく連結されて渡ること」「文字数見積もりの計算が正しいこと」は既存の `nano.test.ts` のパターンで単体テスト化する。ただし **実際のトークン消費量や実モデルの挙動はモックでは検証できない**（`CLAUDE.md` に既述のとおり、テストスイート全体が実 Nano に対して一度も実行されていない）ため、実機確認が別途必須。

### 5.2 指示追従性の検証（人手による定性評価が必須）

自動採点は行わない。理由: 応答が指示に従っているかを機械的に判定するには別の LLM 判定者（judge）が要るが、クラウド LLM へのフォールバックは非交渉制約で禁止されており、Nano 自身に自己採点させても信頼性がない。したがって以下の**手動チェックリスト方式**を提案する。

1. 長さの異なる 3〜5 段階のテスト用プリセットを用意する（例: 短文「関西弁で話す」、中文「丁寧語・敬語のみ、絵文字禁止、回答は必ず3行以内」、長文「詳細な設定＋口調のサンプル文＋禁止ワードリスト」など）。
2. 各プリセットに対して、指示と無関係な標準的な質問セット（5〜10 問、雑談・技術質問・要約依頼など）を実 Chrome で投げる。
3. 各応答について、指示（口調・禁止事項・フォーマット）が守られているかを人間が目視で判定し、簡単な○/△/×で記録する。
4. 結果を本ドキュメントの付録（または `docs/` 配下の別ファイル）に記録し、それを根拠にデフォルトの推奨上限文字数と、管理 UI の注意書き文言（例:「指示は目安であり、必ず反映されるとは限りません」）を確定する。
5. one-shot 例（「例: ユーザー『調子どう？』→ アシスタント『まあまあやな』」のような実例をプリセット内に書かせる）を入れた場合と入れない場合で追従率に差が出るかも合わせて確認し、管理 UI のプレースホルダー・ヘルプ文言に反映する。

この 5.2 の結果が出るまでは、機能自体は「ベストエフォートの指示」であることを UI 上に明記して先行リリースし、確定後にコピーと上限値を調整する 2 段階リリースを想定する。

## 6. 既存機能・非交渉制約への影響確認

- **外部通信ゼロ**: プリセットの保存・読み込みはすべてローカルストレージ／IndexedDB で完結し、5.2 の検証も含めてクラウド判定 LLM 等は一切使わない。新規依存追加も不要。
- **アプリの `messages[]` が正**という原則は変わらない。プリセットは `Thread` のメタデータであり、セッションはこれまでどおり使い捨てのキャッシュ。
- **履歴は暗号化しない**という既存方針と同様、プリセット本文も平文保存になる。個人的な指示（機微な性格設定など）を書く用途も想定されるため、ガイド（`guide-content.ts`）の「履歴の保存方法」セクションにプリセットと常時適用する指示の扱いを追記済み。
- **`_headers` の CSP・`verify:network` への影響なし**（新規外部リクエストが発生しない機能のため）。
- `MetricsStore`（`metrics.ts`）は内容を一切記録しない方針を維持し、プリセットや指示に関する数値も記録しない（実装なし）。
- **「全履歴を削除」との関係（実装時に確定）**: プリセット・常時適用する指示を毎回自動で削除すると運用上不便という判断から、既定では「全履歴を削除」の対象外とした（`KEEP_ON_CLEAR` / IndexedDB の `meta`・`presets` ストアを `clear()` の対象から除外）。ただし完全に消せないのも不便なため、削除確認ダイアログにチェックボックスを設け、削除の都度「指示類も含めて消すか」を選べるようにした（既定はオフ ＝ 残す）。
- **バックアップとの関係（実装時に確定）**: エクスポート/インポート（`exchange.ts` v3）にプリセット・常時適用する指示を含めた。インポート時、プリセットは ID で追加/上書きし、常時適用する指示はインポート元に値がある場合のみ現在の設定を上書きする（空のバックアップで誤って消さないため）。

## 7. 実装フェーズ案（実施結果）

1. **フェーズ A（データ層・単一プリセット）— 実装済み**: `PromptPreset` の CRUD、`history.ts` / `history-idb.ts` へのコレクション追加、`nano.ts` への合成ロジック（`setPreset`）、単体テスト。管理ダイアログ（`PresetsDialog.tsx`）を追加。
2. **フェーズ B（トップページからの選択）— 実装済み**: `Chat.tsx` にプルダウンを追加し、`Thread.presetId` との連動、`exchange.ts` の v3 対応（エクスポート/インポート）。
3. **フェーズ A/B 完了後に追加された作業（当初計画にはなかったもの）— 実装済み**: 「常時適用する指示」（プリセットとは別のグローバル 1 枠、オン/オフなし）を追加。「全履歴を削除」からの除外/削除選択、バックアップへの追加も実装した（6 章末尾）。
4. **フェーズ C（検証結果の反映）— 未実施（予備確認のみ、5 章）**: 5.1・5.2 で定義した手順どおりの実機検証はまだ行っていない。推奨文字数・警告文言・ガイド記載の見直しは、この検証の後に行う。

## 8. 未決事項（更新）

- ~~プリセットをアプリ全体の既定値にする（毎回同じものを使う）か、スレッドごとに個別選択にするか~~ → **決定**: プリセットはスレッドごとの選択、加えて別枠の「常時適用する指示」をアプリ全体の既定値として持つ二本立てにした（7 章 3.）。
- ~~プリセットの言語（ja/en）を分けて持つか、自由記述 1 本にするか~~ → **決定**: 自由記述 1 本のまま。`SYSTEM_PROMPT[lang]` の言語強制はプリセット・常時適用する指示と独立に維持している。
- ~~「全履歴を削除」でプリセットをどう扱うか／バックアップに含めるか~~ → **決定**（6 章末尾）: 既定では「全履歴を削除」の対象外とし、削除確認のチェックボックスで選べるようにした。バックアップ（エクスポート/インポート）には含める。
- **残課題**: 5.2 の実機検証（手動チェックリスト方式）をいつ・誰が実施するか、結果をどのファイルに残すか（本書への追記か、`docs/` 配下の新規ファイルか）は未定のまま。
